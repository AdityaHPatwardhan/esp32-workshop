Part 1

Hello, ESP32

Get code onto a chip, without installing anything.

  1. Wire the ESP32-CAM to the USB-TTL adapter: TX and RX cross, power on 5V
  2. To flash: IO0 → GND, press RESET
  3. Launchpad Settings → baud 230400 → Connect
  4. To run: remove IO0, press RESET
The ESP32-CAM has no USB port, so it talks to the laptop through a USB-TTL adapter. TX goes to the other side's RX (one talks, the other listens). Power goes on the 5V pin; VCC is an output, not an input. The adapter can't reset the board for us, so we do it by hand: IO0 low during RESET means "wait to be flashed". Remove it and reset to run. 921600 baud (Launchpad's default) is too fast over jumper wires: 230400 works. The setting is greyed out while connected and resets when the page reloads. Windows: CP2102 needs the Silicon Labs CP210x driver if no COM port shows up (CH340 adapters: WCH CH341SER driver).
How we'll flash

Flashing straight from the browser

Answering "how do I share binaries": ESP Launchpad is Espressif's web flasher built on esptool-js (the JavaScript port of esptool). It reads a small TOML file that lists the binaries, so we host our .bin files + TOML on GitHub Pages and give one link. Web Serial works only in Chrome/Edge on desktop (not Firefox, not Safari, not phones).

void app_main(void)       // your code starts here
{
    printf("Hello World from %s!\n", CHIP);

    gpio_reset_pin(LED);
    gpio_set_direction(LED, GPIO_MODE_OUTPUT);

    while (1) {
        gpio_set_level(LED, 1);   // on
        vTaskDelay(pdMS_TO_TICKS(500));
        gpio_set_level(LED, 0);   // off
        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

Inside the ESP32-S3

Ask: "Where is our Blink program stored right now?" → in the external flash chip. "If it's outside the chip, how does the CPU run it?" → the chip reads it from flash over SPI as it runs (more in the boot flow).
Memories

Fast & small … or big & slow

Kept at power-off?Used for
ROM✅ forever, read-onlyboot code
SRAM❌variables, stacks
PSRAM❌big buffers, images
Flash✅ (wears out slowly)program, AI model, settings
Analogy: SRAM = your desk (small, instant), PSRAM = the bookshelf behind you, flash = the library (huge, keeps everything, slower). ROM = the instructions printed on the desk itself. Flash can be erased ~100,000 times per sector: don't write it every second.
Pressing reset

From power-on to app_main()

Ask: "Why doesn't the ROM just start our app directly?" → ROM is fixed forever. Anything that needs to change (partition layout, OTA updates, security) lives in the updatable 2nd-stage bootloader.

From C to volts

How does the LED actually turn on?

W1TS = "write 1 to set": only the bits you write as 1 change. The Blink firmware has a BLINK_USE_REGISTERS option that does exactly this with REG_WRITE, no driver. LED on GPIO2 on most ESP32-S3-CAM boards (GPIO3 on the S3-EYE); confirm on the real board. Some LEDs are wired the other way (active-low): writing 0 turns them on.

Part 3

Machine Learning on ESP32

Neurons, weights, training, and squeezing a neural network into 300 KB.

Words first

AI ⊃ ML ⊃ Deep learning ⊃ TinyML

  • AI: machines doing "smart" things
  • ML: learning the rules from examples instead of writing them
  • Deep learning: ML with neural networks of many layers
  • TinyML: running them on microcontrollers, using milliwatts
The big idea

Don't write the rules. Learn them.

The building block

One neuron: multiply, add, decide

Weights = how much each input matters. Bias = how easily it fires. ReLU: negative → 0.

w₁
w₂

Interactive: drag the sliders (click a slider first; arrow keys then move it, click outside to get slide keys back). Make the neuron fire, then make it go silent by turning a weight negative. A neuron is nothing magical: multiply each input by a weight, add them up, add a bias, then squash negatives to zero. Our person model has ~300,000 weights. "Learning" = finding good values for all of them.
Stack thousands of them

Layers find patterns, then patterns of patterns

Nobody programmed "detect an edge" or "detect a head". Training discovered these filters by itself. Shapes shown are illustrations of the idea.
How it learns

Training: guess, check, adjust … a million times

Our model was trained on

  • Visual Wake Words dataset
  • ~100,000 photos from COCO, labelled person / no person
  • On a GPU, for hours

After training the weights are frozen. The board never learns, it only uses them.

Each pass nudges every weight a tiny bit in the direction that would have reduced the error. Repeat over the whole dataset many times (epochs). Ask: what happens if the dataset has no photos of people wearing masks, or only daytime photos? (bias in data → bias in model.)

Know its limits

"Is there a person?" ≠ "How many, and where?"

Classifier (today)

One answer for the whole image. Tiny and fast.

Detector (next step)

Boxes + count. Bigger model, needs PSRAM: ESP-DL / ESP-WHO.

Ask: "It says 'person', but can it count three people?" → no. Counting needs a detection model (e.g. ESP-DL pedestrian detection or a YOLO-style model), which needs more RAM and time per frame. Also ask: what happens at a 30% threshold vs 90%? (false alarms vs missed people.)
Part 5

Device · Phone · Cloud

How a smart plug really works: Wi-Fi setup, HTTPS, MQTT, and ESP RainMaker.

ESP32-S3-DevKitC-1: Espressif
The connected-device triangle

Three links, three protocols

  • Phone ↔ ESP32: Bluetooth LE, only when close. Used to set up Wi-Fi.
  • ESP32 ↔ Cloud: always-on, tiny messages. Device can't be reached from outside, so it connects out.
  • Phone ↔ Cloud: normal app/web traffic, from anywhere.
Key insight: your phone in another city can't connect to a device behind your home router (NAT, no public IP). So both connect OUT to a cloud server, which relays messages.
Step 0

How does a device without a screen get your Wi-Fi password?

This is ESP-IDF's "wifi_provisioning" component; RainMaker uses it. Compare with how we did it in Part 4: Wi-Fi was baked into the firmware, which is fine for a workshop but not for a product sold to millions of homes.
Security

HTTP is a postcard. HTTPS is a sealed envelope.

✉️ HTTP

Anyone on the path (café Wi-Fi, ISP) can read and change it.

🔒 HTTPS = HTTP + TLS

① Who are you? server shows a certificate signed by a trusted authority
② Agree on a secret key without ever sending it
③ Encrypt everything with that key

The ESP32-S3 has hardware AES, SHA and RSA/ECC accelerators (Part 2's peripheral list), so TLS is fast even on a microcontroller. The trusted certificate authorities are stored in flash (the "CA bundle"). With RainMaker the device also has its own certificate, so the cloud knows which device it's talking to (mutual TLS).
The device's language

MQTT: publish / subscribe

  • Devices publish to topics, others subscribe
  • One long-lived connection, kept open by the device
  • So the cloud can push "turn on" instantly
  • Messages can be just a few bytes
Compare with Part 4: our UDP broadcast was "shout to everyone in the room". MQTT is "post to a named noticeboard that anyone, anywhere, can follow", through a server, encrypted with TLS.
All of it, ready-made

ESP RainMaker

The firmware just says "I'm a switch with a power toggle". The app draws the button, the cloud does the rest. No server code to write.

RainMaker is Espressif's IoT cloud platform. The device describes itself (device type, parameters like power/brightness), and the phone app generates its UI from that description. Same building blocks as the previous three slides: BLE provisioning, MQTT over TLS, HTTPS REST.
